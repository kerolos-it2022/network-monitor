# 🌐 Bilingual UI (Arabic + English)

**English** · [العربية](I18N.ar.md)

The application ships with two interface languages and one setting that switches everything. English is the
default and Arabic stays first-class; the two are complete peers. This document explains the model, how to
add text, and the rules that keep both languages in sync.

## The one setting

| Where | What |
|---|---|
| Dashboard → top bar | The 🌐 button switches the language instantly for the whole UI |
| Server setting | `app_settings.ui_language` (`ar` \| `en`), seeded from `NM_UI_LANGUAGE`, default `en` |
| API | `GET /api/settings/ui-language` (public — the login and public pages need it) · `PUT` (admin only, written to the audit log) |
| Browser cache | `localStorage['nm.lang']` mirrors the setting so `lang`/`dir` are correct **before the first paint** (a tiny inline script in each page's `<head>`) |
| Propagation | The public status page and the NOC screen are part of the same setting: change it in the dashboard and all three surfaces follow |
| Visitor override | The public page and the NOC screen carry the same 🌐 button, but there it switches **that device only** and never writes the server setting — a visitor reading Arabic does not change the language for everybody (`localStorage['nm.langChoice']` marks that explicit choice, and the server setting is then seeded without being stored) |

Switching the language sets `<html lang>` and `<html dir>` and flips the layout between RTL and LTR. The
dashboard keeps the current tab open — it re-runs that section's loader so rows built by JavaScript come
back in the new language.

## The engine

| File | Role |
|---|---|
| `frontend/public/js/nm-i18n.js` | The dictionary (`DICT.ar`), `registerLang`, `t(key, vars)`, `setLang`, `applyDom`, `coverage()`, and the global `T(key, fallback)` helper |
| `frontend/public/js/nm-i18n-en.js` | The English dictionary — must stay key-for-key identical |
| `frontend/public/js/nm-format.js` | Language-aware formatting: dates, times (ص/م ⇄ AM/PM), durations, byte sizes, relative time (“قبل ٥ دقائق” / “5 minutes ago”), plural forms |
| `frontend/public/js/nm-lang.js` | The top-bar button, the server round-trip, and the active-section redraw |
| `frontend/public/js/nm-log-i18n.js` | Render-time translation of the **stored notification messages** (see below) |

Translation happens in two ways:

- **DOM**: any element carrying `data-i18n="key"` gets its text replaced; `data-i18n-attr="placeholder:key
  title:key.title"` does the same for attributes. One pass over the document covers the whole page.
- **JavaScript**: `NMI18N.t('key')` (or the global `T('key', 'Arabic fallback')`) inside code that builds
  markup. Keep the Arabic string as the fallback argument so the UI never shows a raw key.

If a key is missing from the English dictionary, `t()` falls back to the Arabic text — the UI degrades to
Arabic, never to a `key.name` placeholder.

## Adding a new string

1. In markup: `<span data-i18n="key.name">النصّ العربي</span>`, or attributes through
   `data-i18n-attr="placeholder:key.name title:key.title"`.
2. In JavaScript: `NMI18N.t('key.name')` with the Arabic fallback.
3. Add the key to **both** dictionaries — `backend/test/i18n.test.js` fails if an Arabic key has no English
   counterpart (it also checks a set of LTR rules in `ui.css`).
4. Never translate: program values (`lan`, `ping`, `zone`…), user data (device names, locations, vendor
   strings), platform names (ngrok, SNMP, SSE) and provider error text.

## Layout in LTR

Section 17 of `css/ui.css` holds the `html[dir="ltr"]` overrides: table and column alignment, the time
input's forced LTR, gradients, the sidebar's slide direction, map-zone rotation and value cells. A few
surfaces keep an explicit `dir="rtl"` on purpose (the topology canvas and the NOC drawn board) because their
coordinates are physical. Bump the stylesheet version query (`ui.css?v=…`) in the four pages whenever the
stylesheet changes, so browsers re-read it.

## Notification messages: one language, chosen on the server

The language of the messages the system **sends** — Telegram, WhatsApp, mobile push, the Telegram bot
replies and buttons, escalation and its reminder, the storm digest, the daily report, the engine watchdog,
the test notification — is its **own setting**, independent of the interface language:

| Where | What |
|---|---|
| Notification screen | The 🌐 button beside “Sent notification and log language” switches the sent messages and the log view together |
| Server setting | `app_settings.notification_language` (`ar` \| `en`), seeded from `NM_NOTIFICATION_LANGUAGE`, default `en` |
| API | `GET /api/settings/notification-language` (any signed-in session — the screen reads it) · `PUT` (admin only, written to the audit log) |

It has to live on the server: the messages are built and sent by the server, at any hour, with no browser
open (a device can drop at three in the morning). An administrator's click changes it for the whole
installation; a viewer account that may not write keeps its own view of the log only.

Both languages are compiled at send time from the same template pair (`message-i18n.service.js`), and the
English wording is written to equal what the log's render-time translator produces for the Arabic row — so
the log reads the same whether a message was sent in English or stored in Arabic and translated for
display. `backend/test/log-i18n.test.js` pins that equality byte for byte, scenario by scenario.

Stored rows are **not** rewritten: a message keeps the wording it was sent with. Rows stored in Arabic are
translated for display by the rules in `nm-log-i18n.js` (one rule per template, line-by-line and
all-or-nothing — an unknown line is shown exactly as stored, so a half-translated message can never
appear); rows already stored in English are shown as they are. User data inside a message (device names,
IPs) is copied verbatim in both languages, Arabic-Indic digits and `toLocaleString('ar')` timestamps become
Latin in the English text, and Telegram `<b>/<code>` tags are stripped in both.

**Maintainer contract:** changing or adding a message template means updating the matching rule in
`nm-log-i18n.js` — `backend/test/log-i18n.test.js` fails when a rule's Arabic needle no longer exists
verbatim in the backend sources — and adding the English twin next to the Arabic template, because the same
test asserts that the English it sends equals the English the log displays for that Arabic text.

Deliberate Arabic remainders: free-text provider errors and any new template until a rule (and its English
twin) is added. The daily report's AI analysis is the one part that is always bilingual — it appears twice,
under `🧠 تحليل AI:` and `🧠 AI analysis:`, because its readers do not share a language.

## Current state

- Complete UI coverage: dashboard (all tabs), login page, public status page and NOC screen.
- Notification messages follow their own server setting (`notification_language`): one language per message,
  the same language on every channel, switchable in one click.
- Server-rendered pages (the weekly printable report and the QR label sheet) are Arabic today.
- English is the default for a fresh install; the switch is one click away and stored on the server, so every
  browser and the wall screen agree — and a visitor can still override the language of their own device.
